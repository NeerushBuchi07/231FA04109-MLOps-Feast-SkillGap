# Curriculum-Industry Skill-Gap Feature Store using Feast

This project implements a local feature store using **Feast** to manage, serve, and utilize student employability features for predicting industry readiness. By utilizing a central registry, Feast facilitates both offline historical feature retrieval for model training and low-latency online retrieval for real-time inference.

## Problem Statement

The **Curriculum-Industry Skill-Gap** represents a critical mismatch between the theoretical knowledge taught in traditional university academic curricula and the practical skills, technologies, and soft skills demanded by the modern job market. Universities often prioritize foundational and conceptual understanding (e.g., core database theory or raw language syntax) over real-world application, modern development practices (e.g., Docker, Kubernetes, CI/CD), and critical soft skills (e.g., presentation, adaptability, teamwork). 

By building a student feature store, we can continuously track academic progress, technical skill mastery, soft skills, and extracurricular contributions. A machine learning model integrated with a feature store like Feast can help identify students' readiness and highlight critical gaps in real-time, allowing educational institutions and students to take targeted actions.

## Feature Engineering

The following aggregated and encoded features were engineered to capture a student's readiness:

1.  **`total_technical_skills_score`**: The sum of scores across all 18 technical skills. (Value range: $0$ to $1800$).
2.  **`total_soft_skills_score`**: The sum of scores across all 7 soft skills. (Value range: $0$ to $700$).
3.  **`total_extracurricular_score`**: The sum of counts and scores from extracurricular indicators (`Internships`, `Projects`, `Hackathons`, `Certifications`, `LeetCode`, `GitHub_Repos`).
4.  **`overall_readiness_score`**: A weighted aggregate index indicating a student's overall potential:
    $$\text{overall\_readiness\_score} = (\text{CGPA} \times 10) + (\text{total\_technical\_skills\_score} \times 0.5) + (\text{total\_soft\_skills\_score} \times 0.7) + (\text{total\_extracurricular\_score} \times 1.0)$$
5.  **`Industry_Ready_Encoded`**: An integer mapping of the target variable `Industry_Ready` for classification compatibility:
    *   `Not Ready` $\rightarrow 0$
    *   `Moderately Ready` $\rightarrow 1$
    *   `Industry Ready` $\rightarrow 2$
6.  **`event_timestamp`**: A dummy timestamp column generated by assigning incremental seconds starting from `2023-01-01 00:00:00` for each row, satisfying Feast's temporal ingestion requirement.

## Feast Architecture

Below is the workflow showing how raw data flows through feature engineering into the offline and online stores via Feast:

```
Original Dataset
      ↓
Feature Engineering
      ↓
Parquet Offline Data
      ↓
Feast FeatureView
      ↓
 ┌─────────────────────┐
 ↓                     ↓
Historical Features   Materialization
 ↓                     ↓
Model Training       Online Store (SQLite)
                       ↓
                  Online Retrieval
                       ↓
                    Prediction
```

## Implementation

The feature store is implemented with the following key components:

*   **Entity:** `student_id` (defined with a `ValueType.STRING`). It represents the unique student identifier used as the primary key for lookup and joining operations.
*   **Data Source:** `FileSource` pointing to `data/employability_features.parquet` (the offline store), using `event_timestamp` for versioning.
*   **FeatureView:** `employability_features` registers the student entity, specifies a Time-To-Live (TTL) of 365 days, and points to the parquet data source. Features are automatically inferred by Feast from the parquet file's schema.
*   **Historical Retrieval:** Executed via `store.get_historical_features()`. It takes a query dataframe of entities and timestamps and performs a point-in-time join to retrieve the matching features without data leakage, outputting a training dataframe.
*   **Model:** A `RandomForestClassifier` (100 estimators) trained using the retrieved historical features (`CGPA`, `total_technical_skills_score`, `total_soft_skills_score`, `total_extracurricular_score`, and `overall_readiness_score`) to classify the target label `Industry_Ready_Encoded`.
*   **Online Retrieval:** Executed using `store.get_online_features()` by supplying student entity rows. Features are fetched instantly from the SQLite online database (`online_store.db`), which is populated by materialization.

## Analytical Questions & Answers

### 1. What is the entity in your Feast implementation?
The entity in this implementation is **`student_id`**. It is defined as a Feast `Entity` with a string value type. In a feature store, an entity acts as the primary key or join key used to query and group related features together (analogous to a primary key in a database table).

### 2. List the features stored in your FeatureView.
Because Feast infers features directly from the data source's schema in this implementation, the `employability_features` FeatureView stores all column fields in the Parquet file (excluding the entity key `student_id` and the timestamp `event_timestamp`). These are:
*   **Original Fields:** `CGPA`, `DSA`, `Python`, `Java`, `C++`, `SQL`, `DBMS`, `Operating_System`, `Computer_Networks`, `OOPS`, `React`, `NodeJS`, `MongoDB`, `Git`, `Linux`, `AWS`, `Docker`, `Kubernetes`, `Machine_Learning`, `Communication`, `Presentation`, `Teamwork`, `Leadership`, `Critical_Thinking`, `Problem_Solving`, `Adaptability`, `Internships`, `Projects`, `Hackathons`, `Certifications`, `LeetCode`, `GitHub_Repos`, and `Industry_Ready`.
*   **Engineered Fields:** `total_technical_skills_score`, `total_soft_skills_score`, `total_extracurricular_score`, `overall_readiness_score`, and `Industry_Ready_Encoded`.

### 3. Explain how one feature was calculated.
Let's take **`overall_readiness_score`** as an example. It combines academic achievements with technical capability, soft skills, and extracurricular records to form a unified score:
*   First, `CGPA` (initially out of $10$) is multiplied by $10$ to scale it to the same order of magnitude as test scores (out of $100$).
*   Second, the total technical skills score (maximum sum of $1800$) is scaled down by $0.5$.
*   Third, the total soft skills score (maximum sum of $700$) is scaled by $0.7$.
*   Fourth, the extracurricular activity score is added directly (scaled by $1.0$).
*   The final formula is:
    $$\text{overall\_readiness\_score} = (\text{CGPA} \times 10) + (\text{total\_technical\_skills\_score} \times 0.5) + (\text{total\_soft\_skills\_score} \times 0.7) + (\text{total\_extracurricular\_score} \times 1.0)$$

### 4. What is the difference between your original dataset and the feature dataset?
*   **Original Dataset (`Employability_Dataset.csv`):** A static, flat CSV file containing 34 columns. It contains a mix of text columns (e.g. `Student_ID`, `Industry_Ready`), has no notion of timestamps, and only represents raw measurements.
*   **Feature Dataset (`employability_features.parquet`):** A column-oriented Parquet file optimized for storage and read efficiency. It:
    1.  Renames the ID column to `student_id` to align with the Feast entity name.
    2.  Appends an `event_timestamp` column to support point-in-time correctness.
    3.  Contains engineered aggregated features (`total_technical_skills_score`, `total_soft_skills_score`, `total_extracurricular_score`, `overall_readiness_score`, `Industry_Ready_Encoded`).

### 5. What is the purpose of the offline store?
The offline store is designed to save historical feature data (typically stored in a data warehouse like BigQuery, Snowflake, or local Parquet files). Its main purpose is to allow ML engineers to reconstruct historical training datasets. By specifying entity keys and event timestamps, Feast queries the offline store to perform "point-in-time" joins, which retrieve feature values exactly as they were at that moment in time, avoiding data leakage during model training.

### 6. What is the purpose of the online store?
The online store is a low-latency database (like Redis, DynamoDB, or SQLite locally) that stores only the *latest* feature value for each entity key. Its purpose is to support real-time predictions. When a model is running in production and needs features to predict industry readiness for a student, it queries the online store using the student's ID, returning features in sub-milliseconds rather than recalculating them or querying a slow data warehouse.

### 7. What is the purpose of feast apply?
The `feast apply` command parses the feature definitions (configured in `feature_store.yaml` and python files containing `Entity` and `FeatureView` definitions) and updates the central registry (e.g. `registry.db`). It also updates the infrastructure of the online store (such as creating the tables in the SQLite database to accommodate the new feature views).

### 8. What does materialization do?
Materialization extracts feature values from the offline store (Parquet file) for a given time window and loads/writes the latest values into the online store (SQLite). This fills the online database with current feature values so they are ready for real-time querying.

### 9. What is the advantage of retrieving features through Feast instead of manually calculating them separately during training and prediction?
*   **Prevents Training-Serving Skew:** The same feature definition code is used to query both training data (offline) and live inference data (online). This guarantees that features are calculated identically in both environments, preventing model degradation in production.
*   **Feature Reusability:** Different models and teams can reuse registered features without writing duplicate ETL code.
*   **Decouples Engineering and ML:** Data engineers can update the offline/online feature pipeline independently, while ML models consume features through a standard API.

### 10. State two limitations of your current dataset.
*   **Synthetic Timestamp Generation:** The `event_timestamp` values are synthetic and sequential. In a real scenario, features change sporadically over time as students learn skills or graduate. The lack of true historical changes limits the demonstration of Feast's point-in-time correctness.
*   **Severe Class Imbalance / Missing Categories:** The target label contains only `Industry Ready` and `Moderately Ready` students, and lacks any `Not Ready` student entries. This will bias the model to never predict a student as "Not Ready," making it ineffective for identifying at-risk students.

### 11. State two ways your feature store could be improved when more curriculum and industry evidence becomes available.
*   **Streaming Ingestion for Real-Time Updates:** By setting up Feast Push Sources or Kafka integrations, online features can be updated instantly whenever a student completes a GitHub commit, solves a LeetCode problem, or completes a quiz on the LMS system.
*   **Modular Multi-Entity Architecture:** Adding new entities like `course_id` (curriculum) and `job_id` (industry requirements) would allow joins between university courses, student profiles, and job description skills, helping to model direct gaps between current courses and industry demands.
